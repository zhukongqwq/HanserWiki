# 文档更新采用文件级核对（Android 与 Windows 一致）

## 背景

文档更新源（GitHub Release 的 `list.json`，{路径: sha256}）实现早期采用「清单级核对」：客户端把上次下载的 `list.json` 缓存（`.sync-list.json`），本次下载的清单与缓存 sha 一致即整轮跳过，不再触碰本地文件。该语义依赖发布端「清单不变则文件必不变」的假设。

## 决策

两端（Windows `GitHubSync.cs` 与 Android `GitHubSync.kt`）的文档更新**每次调用都做文件级核对**：

1. 下载 `list.json`；
2. 解析全部条目（缓存一致仅输出提示日志，不跳过）；
3. 对清单中每个文件计算本地 sha256 并与清单值比对；
4. 仅下载缺失或哈希不一致的文件（raw + 镜像，下载后二次校验）；
5. 保存清单缓存并触发增量索引。

Android 端该流程运行在**前台服务**中（通知栏常驻进度，可后台下载），完成发结果通知。

## 理由与取舍

- 用户报告 Android 端「清单一致即跳过」导致本地文件被误删/损坏时不会修复；文件级核对保证本地库与发布清单**最终一致**，代价是每次点击多一次全量本地 sha256 扫描（docx 库规模下开销可忽略）。
- 曾考虑保留清单级短路 + 「强制核对」开关：两种语义并存易让用户困惑，且核对成本极低，故统一为无条件文件级核对。

## 后续

发布端无需改动（同一 `list.json` 协议）。
